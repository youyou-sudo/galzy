# 探索现有方案

先扫市场，再谈自研。目标不是凑一篇中立综述，而是给出带判断的候选清单。

## 触发条件

**使用当：**

- 在头脑风暴、技术选型、build-vs-buy 或架构决策之前
- 用户要求"先探索现成方案"、"看看 GitHub/npm/pip/文档"
- 你怀疑第三方库、框架或服务已经覆盖了大部分需求
- 你需要判断某个生态里的主流做法，而不是直接拍脑袋自研

**不使用当：**

- 问题纯粹是内部业务规则或仓库私有约定，外部现成方案几乎不相关
- 用户明确要求只讨论当前仓库内部实现，不考虑外部依赖

## 路由指令

主代理加载此 skill 后，**直接派遣 `@调研工程师`** 子代理执行探索任务。

传递给 `@调研工程师` 的上下文应包含：

- 要探索的主题或问题
- 项目技术栈线索（如语言、运行时、框架，帮助确定搜索生态）
- 功能需求简述（用于质量筛选的匹配度判断）
- 如有偏好或禁忌（如 license 要求、必须支持某 runtime），一并传入

## 输出格式定义

主代理期望从 `@调研工程师` 收到：

- **推荐** — 1-2 个真正值得继续看的候选项
- **次选** — 可行但有明显短板的候选项
- **淘汰** — 明确不推荐的候选项及淘汰理由
- **质量信号** — 维护新鲜度、生态采用度、文档/API 质量、项目匹配度
- **探索结论** — 对 build-vs-buy 的推荐输入：直接集成 / 在现有方案上扩展 / 没有合格方案再考虑自研

这是上游选型流程的决策输入，不替代最终设计方向拍板。
